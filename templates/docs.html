02

Protocol

Authorization Code with PKCE

  1. 1
    Create a verifier

    Generate a high-entropy verifier and its S256 challenge.

  2. 2
    Push, then authorize

    Optionally POST the request to PAR, then send its short-lived reference through the browser. Direct requests remain supported.

  3. 3
    Exchange once

    POST the short-lived code and original verifier to the token endpoint.

  4. 4
    Validate

    Verify the ID token signature, issuer, audience, expiry, and nonce.

  5. 5
    Refresh safely

    Request offline access only when needed, persist the refresh token securely, and replace it after every use.

Protect the authorization response.Use response_mode=query.jwt or form_post.jwt to receive one audience-bound RS256 JARM response. Unsigned form_post remains available when URL exposure is the only concern.
Require signed authorization requests.Configure dedicated request_object_jwks and enable require_signed_request_object. Public clients remain public: these keys verify JAR Request Objects and are never accepted as token-endpoint credentials.
Bind silent SSO to the expected subject.Send a prior ID Token as id_token_hint. Robine ID verifies its issuer, signature, retained key, and exact client audience, then only reuses a browser session for the same subject. The hint is never accepted as a credential.
End sessions with an exact return target.RP-Initiated Logout accepts GET or form POST and always requires confirmation. Identify the application with id_token_hint, client_id, or both; the return URI must exactly match that application's registered post-logout URI. Participating RPs can also receive session-bound Front-Channel and Back-Channel Logout notifications.
Monitor the OP session.HTTPS discovery publishes check_session_iframe, and every successful Authentication Response includes an origin-bound session_state. The iframe validates the registered RP origin, computes locally with Web Crypto, and never exposes the authenticated-session credential.
Request fine-grained access.Use RFC 9396 authorization_details for registered structured permissions. Robine ID validates the type policy, displays the complete escaped request during consent, and lets token or refresh requests remove rights without adding new ones.
Bind tokens to the client key.Send an EdDSA, ES256, or RS256 DPoP proof to the token endpoint. Bound UserInfo calls use the DPoP authorization scheme and a fresh proof containing ath; replay is rejected across instances. Operators can require server-provided nonces with dpop_nonce_required.
Verify introspection provenance.Send Accept: application/token-introspection+jwt from an authenticated resource server to receive an RS256 response bound to that caller. Token data stays inside the token_introspection claim to prevent JWT substitution.
Discover UserInfo safely.Fetch /.well-known/oauth-protected-resource/{{ issuer_id }}/userinfo to discover the exact resource, authorization server, scopes, Bearer method, signed-response algorithm, and DPoP algorithms. UserInfo challenges link back to this document.

Backend service?Authenticate a confidential client at the same token endpoint with grant_type=client_credentials. An explicitly enabled client can exchange its own token for a shorter-lived, downscoped token aimed at another registered resource, and can opt into RFC 8693 actor tokens with a bounded act delegation chain. Service tokens are introspectable and revocable, but never expose UserInfo.
CLI or television?Enable the Device Authorization Grant, display the returned user code and verification URI, then respect the server-provided polling interval. The browser confirmation is session-aware and the final access, ID, and optional rotating refresh tokens can be consumed through another instance.

Safe activation

A complete valid candidate activates atomically; invalid edits leave the prior revision active.

make config-preview
Provision an initial user password safely.Run make user-password BCRYPT_COST=12, deliver the generated 144-bit password once through a trusted channel, and keep only the emitted password_hash in configuration. Use one bcrypt cost for every user in a revision.
Suspend a complete issuer tenant.Set an issuer's enabled field to false. Its protocol routes, metadata, WebFinger advertisement, default-page selection, and automatic key rotation stop resolving it, while the validated declaration and persisted key history remain available for reactivation.
Suspend a relying application atomically.Set an application document's enabled field to false. The registration remains validated and available for reactivation, while client authentication, active grants, browser origins, logout callbacks, and conditional Discovery capabilities stop resolving it.
Bind an application to selected tenants.Set issuer_ids to a non-empty list of configured issuer identifiers. Authentication, protocol grants, browser origins, logout callbacks, and conditional Discovery capabilities then resolve the client only on those issuers; omit the field to preserve all-issuer compatibility.
Suspend an identity without renumbering it.Set a local user's enabled field to false. Login, active sessions, device approval, refresh, token exchange, UserInfo, and introspection stop resolving that user after configuration activation, while the stable internal and pairwise subject mappings remain configured.
Bind an identity to selected tenants.Set a user's issuer_ids to a non-empty list of configured issuer identifiers. Login, session reuse, device approval, active grants, and pairwise subject resolution then work only on those issuers; correct credentials elsewhere receive the same generic failure as an unknown identity. Separate tenants may reuse one login identifier when their explicit issuer lists are disjoint.
Require stronger or recent authentication.Add totp to authentication.methods, run make totp-secret, and set a user's totp_secret_reference to the environment secret containing that canonical Base32 key. Run make recovery-codes to provision an optional operator-managed set and retain only the emitted recovery_code_hashes. Set an interactive application's required_acr to urn:robine-id:acr:password+totp and optionally set max_authentication_age in seconds. Stale or weaker UserInfo tokens receive an RFC 9470 step-up challenge; accepted TOTP steps and recovery codes cannot be replayed across instances.
Isolate relying-party identities.Set an application's subject_type to pairwise and configure the root pairwise_subject_salt_reference with a durable environment secret of at least 32 bytes. A common redirect host supplies the sector automatically; use a canonical hostname sector_identifier to group multiple trusted hosts deliberately.
Register rich authorization types centrally.Add bounded entries to authorization_detail_types, then opt each application in through authorization_details_types. Removing a type or client permission immediately invalidates affected active grants.
